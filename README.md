# Wallet Service — Overview

The Wallet Service is a digital wallet system that allows creating wallets linked to holders and transferring balances between them. All monetary values are represented in cents (integers).

The project consists of two independent services: `wallet-service` (transactional backend) and `wallet-analytics` (analytics layer).

## Architecture

The system adopts the **Event Sourcing** and **CQRS** (Command Query Responsibility Segregation) patterns.

**Write side (Command):** wallet state is not stored directly in a relational database. Instead, each operation generates a domain event that is persisted in KurrentDB (event store). The current state of a wallet is reconstructed on each operation by replaying all events from its stream.

**Read side (Query):** queries are served from a MySQL projection, kept up to date by an asynchronous consumer that reads events from KurrentDB.

**Analytics side:** a second projection in PostgreSQL is consumed by `wallet-analytics` via dbt for generating analytical marts.

```
HTTP Request (write)
  └─► WalletCommandController
        └─► WalletKurrentDBESHandler (stream replay → Wallet aggregate)
              └─► Wallet.TransferFunds() / NewWallet()
                    └─► Append events to KurrentDB

KurrentDB (persistent subscriptions)
  ├─► WalletKurrentDBConsumer                       → processes incoming transfers
  ├─► WalletKurrentDBProjectorConsumer (MySQL)      → wallet_projections / transfer_projections
  └─► WalletKurrentDBProjectorConsumer (PostgreSQL) → wallet_projections / transfer_projections

HTTP Request (read)
  └─► WalletQueryController → queries MySQL

PostgreSQL
  └─► wallet-analytics (dbt) → staging views → mart_wallets / mart_transfers
```

## wallet-service

Deployed as a monolithic binary (`cmd/monolith`). On startup, it creates three persistent subscriptions in KurrentDB and starts the HTTP server.

### Domain Model

**`Wallet` aggregate:** encapsulates the balance and transfer history. Enforces the following business rules:

- Incoming transfer that exceeds the maximum limit: `ErrBalanceLimitExceeded`
- Insufficient balance for transfer: `ErrInsufficientBalance`
- Duplicate transfer (same ID): `ErrDuplicateTransfer`
- Category not provided: defaults to `unclassified`

Valid categories: `food`, `fuel`, `sports`, `health`, `travel`, `essentials`, `entertainment`, `unclassified`.

**Domain events:**

| Event                        | Generated by            |
| ---------------------------- | ----------------------- |
| `WalletCreatedEvent`         | wallet creation         |
| `FundsTransferredEvent`      | debit (sender side)     |
| `FundsTransferReceivedEvent` | credit (recipient side) |

The `FundsTransferredEvent` is consumed asynchronously by `WalletKurrentDBConsumer`, which loads the recipient wallet and emits the `ReceiveFundsTransfer` command, closing the transfer cycle.

### HTTP API

| Method | Route                         | Description                           |
| ------ | ----------------------------- | ------------------------------------- |
| `POST` | `/wallets`                    | Creates a wallet                      |
| `POST` | `/wallets/{id}/transfer`      | Initiates a transfer                  |
| `POST` | `/wallets/{id}/mock-transfer` | Simulates receiving a transfer        |
| `GET`  | `/wallets`                    | Lists wallets by holder (`holder_id`) |
| `GET`  | `/wallets/{id}`               | Retrieves a wallet by ID              |
| `GET`  | `/wallets/{id}/transfers`     | Lists transfers for a wallet          |

## wallet-analytics

A dbt project that reads PostgreSQL projections and produces two marts:

**`mart_wallets`:** per-wallet summary with current balance, favourite category, status (`active` or `suspended` based on last activity in the past 90 days), transfer counts, and total amount moved.

**`mart_transfers`:** transfer history enriched with the balance before and after each transaction, calculated via SQL window functions.

Custom tests validate data integrity: positive balances, correct balance arithmetic, and consistency between counts.

## Local Environment

The development environment is provisioned via Docker Compose:

```sh
docker compose -f sandbox/docker-compose.yaml up -d
```

| Container           | Port        | Purpose                              |
| ------------------- | ----------- | ------------------------------------ |
| `wallet-mysql`      | 3306        | Read projection                      |
| `wallet-postgresql` | 5432        | Analytics projection                 |
| `wallet-kurrentdb`  | 2113 / 1113 | Event store (UI at `localhost:2113`) |

Projection table schemas are in `sandbox/create-wallet-tables-mysql.sql` and `sandbox/create-wallet-tables-postgresql.sql`. The `sandbox/populate-wallet.js` script can be used for data seeding.
